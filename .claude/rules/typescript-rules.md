# TypeScript コーディング規約
* **型の厳格化**: `tsconfig.json` の `strict: true` に従い、`any` 型の使用は厳禁とします。型が不明な場合は `unknown` を使用し、適切に型ガード（Type Guards）を実装してください。
* **非同期処理**: API通信やファイルI/O等の非同期処理には必ず `async/await` を使用し、Promiseチェーン (`.then()`) は避けてください。
* **エラーハンドリング**: 外部システムとの通信エラーは必ず `try/catch` で捕捉し、適切なカスタムエラークラスをスローするか、ログに出力してください。
* **TSDoc** 各関数にはTSDocに準拠したコメントを記載してください。

# アーキテクチャ・デザイン原則
Claudeが自律的にコードを生成・リファクタリングする際は、以下の設計原則を遵守してください。

* **副作用の分離 (Functional Core, Imperative Shell)**: 
  外部APIとの通信、ファイルI/O、データベースアクセスなどの「副作用を伴う処理」と、「計算・ビジネスロジック」は明確に分離してください。計算ロジックは外部依存のない純粋関数（Pure Functions）として実装し、単体テストを容易に保ちます。
* **型駆動開発 (Type-Driven Development)**: 
  ロジックの実装を始める前に、まず扱うドメインデータ（EDINETのレスポンス形式、抽出後の企業財務データ、算出する指標など）の `interface` や `type` を定義してください。型定義をシステムの仕様書として機能させます。
* **フェイルファスト (Fail-Fast)**: 
  外部システムからのレスポンス形式が予期せぬものだった場合や、計算に必須の財務データが欠損していた場合は、デフォルト値（0や空文字列など）で握り潰さず、早期に例外（カスタムエラー）をスローして処理を中断してください。誤ったデータによる無効な分析結果を防ぎます。
* **単一責任の原則 (Single Responsibility Principle)**: 
  1つのモジュール、クラス、関数は1つの役割のみを持つように小さく保ちます。例えば「TDnetから情報をダウンロードする処理」と「XMLをパースする処理」は必ず別々のモジュールに分割してください。


# 静的解析・フォーマット規約（ESLint / Prettier）
* **コードスタイル**: セミコロンあり、シングルクォート推奨、インデントはスペース2マスとします（詳細は `.prettierrc` に準拠）。
* **未使用コードの禁止**: 使用されていない変数やインポート（unused imports）は、コミット前に必ず削除または修正してください。
* **マジックナンバーの排除**: 計算式や条件分岐で使用する固定値は、意味のある名前をつけた定数（`const`）として定義してください。
