# CLAUDE.md

よくあるLLMのコーディングミスを減らすための行動ガイドライン。必要に応じてプロジェクト固有の指示と統合すること。

**トレードオフ:** これらのガイドラインはスピードよりも慎重さを重視しています。些細なタスクについては、状況に応じて適切に判断してください。

## 1. コーディング前に考える

**憶測で進めない。疑問を隠さない。トレードオフを明示する。**

実装する前に:

* 前提条件を明確に述べること。不確実な場合は質問すること。
* 複数の解釈が存在する場合は、それらを提示すること。黙って1つを選ばないこと。
* よりシンプルなアプローチがある場合は、その旨を伝えること。正当な理由がある場合は反対意見を述べる（プッシュバックする）こと。
* 不明な点があれば立ち止まること。何が混乱を招いているのかを明言し、質問すること。

## 2. シンプルさ第一

**問題を解決するための最小限のコード。推測による実装はしない。**

* 要求された以上の機能は追加しない。
* 一度しか使われないコードの抽象化はしない。
* 要求されていない「柔軟性」や「設定可能性」は追加しない。
* 起こり得ないシナリオに対するエラーハンドリングはしない。
* 50行で書けるものを200行で書いた場合は、書き直すこと。

自問すること: 「シニアエンジニアはこれを複雑すぎると言うだろうか？」もしそうなら、シンプルにすること。

## 3. 局所的な変更

**必要な箇所のみに触れる。自分が散らかしたものだけを片付ける。**

既存のコードを編集する場合:

* 隣接するコード、コメント、またはフォーマットを「改善」しない。
* 壊れていないものをリファクタリングしない。
* たとえ自分なら違うやり方をするとしても、既存のスタイルに合わせる。
* 無関係なデッドコードに気付いた場合は、言及するにとどめ、削除はしないこと。

あなたの変更によって孤立したコードが生じた場合:

* **あなた**の変更によって使われなくなったインポート/変数/関数は削除する。
* 求められない限り、以前から存在していたデッドコードは削除しない。

基準: 変更されたすべての行は、ユーザーの要求に直接結びついていること。

## 4. 目標駆動型の実行

**成功基準を定義する。検証されるまでループする。**

タスクを検証可能な目標に変換する:

* 「バリデーションを追加する」 → 「無効な入力に対するテストを書き、それを通過させる」
* 「バグを修正する」 → 「それを再現するテストを書き、それを通過させる」
* 「Xをリファクタリングする」 → 「前後でテストが通過することを確認する」

複数ステップのタスクの場合は、簡単な計画を述べる:

```
1. [ステップ] → 検証: [確認事項]
2. [ステップ] → 検証: [確認事項]
3. [ステップ] → 検証: [確認事項]

```

強力な成功基準があれば、独立してループを回すことができる。「動くようにする」のような弱い基準では、継続的な確認が必要になる。
